# 里程碑治理规则

## 状态定义

| 状态 | 含义 |
|---|---|
| `LOCKED` | 前置里程碑未通过，不允许实现 |
| `PLANNED` | 已规划，但尚未开始 |
| `IN_PROGRESS` | 当前唯一允许主动开发的里程碑 |
| `READY_FOR_ACCEPTANCE` | 实现和证据齐全，等待人工验收 |
| `ACCEPTED` | 用户明确确认通过 |
| `BLOCKED` | 存在无法在当前授权或条件下解决的阻塞 |

同一时刻最多只能有一个 `IN_PROGRESS` 里程碑。

## 门禁流程

```text
LOCKED
  → 前置里程碑ACCEPTED
PLANNED
  → 用户确认启动
IN_PROGRESS
  → 交付物、测试、文档和证据齐全
READY_FOR_ACCEPTANCE
  → 用户验收通过
ACCEPTED
```

验收不通过时，状态退回 `IN_PROGRESS`，记录退回原因和整改项。

## 通用完成标准

每个里程碑进入 `READY_FOR_ACCEPTANCE` 前必须同时满足：

- 里程碑范围内的交付物全部存在；
- 自动化测试、类型检查和格式检查通过；
- 数据迁移已验证，涉及持久化时有恢复说明；
- 关键行为和失败路径有可观察日志；
- 用户文档和开发文档同步；
- 提供可重复的人工验收步骤；
- 提供测试输出、截图、日志或演示数据等证据；
- 列出已知限制和未解决风险；
- 没有未处理的P0/P1缺陷；
- `status.md` 已更新。

## 审批权

- AI或自动化可以建议阶段通过，但不能将里程碑标记为 `ACCEPTED`。
- 只有用户明确表示验收通过，才可更新为 `ACCEPTED`。
- 未经用户确认，不因“功能看起来完成”而提前进入下一里程碑。

## 范围变更

出现以下情况必须先记录变更，再继续开发：

- 新需求改变已确认的数据模型或权限边界；
- 工作内容跨越当前里程碑；
- 引入新的运行服务、数据库或外部依赖；
- 删除或降低已确认的通过标准；
- 修改 `skill/` 与 `studio/` 的边界。

变更记录至少包含：原因、影响里程碑、兼容性、风险、是否需要用户重新确认。

## 缺陷等级

| 等级 | 定义 | 门禁影响 |
|---|---|---|
| P0 | 数据丢失、越权审批、密钥泄漏、跨项目污染 | 必须阻断验收 |
| P1 | 核心流程不可用、无法恢复、正式版本错误 | 必须阻断验收 |
| P2 | 有替代路径的功能缺陷 | 记录后由用户决定是否阻断 |
| P3 | 体验、文案或低风险改进 | 可进入后续迭代 |
