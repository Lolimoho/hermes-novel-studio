# ADR 0001：宿主形态与 UI 架构

- 状态：**Proposed**
- 日期：2026-11-08
- 决策者：项目所有者
- 相关文档：`docs/architecture/repository-structure.md`、`docs/project-management/milestones.md`

## 背景

Novel Studio 需要一个承载创作流程的界面。现有两个可参考的开源实现：

- **ekko-studio**（原 Hermes Studio / Hermes Web UI）：Vue 3 + Koa 2 + Socket.IO + SQLite 的本地优先 Web 工作台，通过 runtime adapter 接入 16 种 agent，BSL-1.1 许可。
- **Pagekin（书童）**：Electron + React 19 + better-sqlite3 的桌面写作软件，按「设定 → 架构 → 蓝图 → 正文」组织，GPL-3.0 许可。

两者代表了两种不同的产品中心：ekko 以**会话**为中心，Pagekin 以**文档**为中心。本项目要做的是"能接不同 agent 的小说创作 Web UI"，必须明确以哪一方为骨架，否则会退化成"带侧栏的聊天工具"。

## 决策

### 1. 形态：纯 Web，不做桌面壳

第一版以浏览器访问为目标，后端服务与前端分离部署，支持局域网/远程访问。

- 不做 Electron/Tauri 壳，不引入本地文件系统直读、本地终端、系统托盘等桌面专属能力。
- 导出、备份等文件操作通过服务端完成，产物以下载形式交付。

### 2. 中心：文档为主体，会话为附注

界面以"作品 → 阶段 → 章节"的文档结构组织，AI 动作是**阶段执行器**，每次产出落到具体的文档版本上。

- 不设以聊天为主视图的首页。
- 对话记录作为运行（run）的审计附注存在，不是创作的主体载体。
- 一个动作对应一次明确的产出（写一章、出一份审稿意见、生成一段修订），而不是开放式闲聊。

### 3. 分层：UI / 领域服务 / 权威数据，Agent 走领域工具

```text
界面层（React）→ 领域服务层（FastAPI）→ Postgres（唯一权威）
                        ↕
                  Agent 适配层（Hermes）
```

- UI 不直连数据库，不持有模型提供商密钥。
- Agent 只能通过领域工具读写小说数据，不授予任意 SQL 变更能力。
- 人工审批动作只存在于领域服务层，Agent 与自动化不可调用。

### 4. Agent 接入：接口按多适配器设计，实现收敛到 Hermes

- 定义统一的 `AgentAdapter` 契约：启动运行、流式输出、工具调用、取消、用量回传。
- 第一版只实现 Hermes 适配器；其他 agent（Claude Code 等 CLI 型）在契约稳定后再接。
- 不复制 ekko 的 `scoped / global` 双配置模式、credential pool、fallback provider chain 等为 16 个 agent 服务的复杂度。

### 5. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React 19 + TypeScript + Vite + Radix UI | 与 Pagekin 同栈，可直接借鉴交互；与 M0 既定选型一致 |
| 后端 | FastAPI（Python） | 与 Hermes（Python）同语言，无需 Node↔Python 桥接 |
| 数据库 | PostgreSQL | 权威事实、版本、审批、审计的需要 |
| 实时 | SSE 承载生成流；WebSocket 仅用于必要的双向场景 | 比 Socket.IO 简单，且与 Python 栈一致 |
| 编辑器 | 待定（ADR 0003） | 需评估 Markdown 编辑与差异对比能力 |

### 6. 许可边界

ekko-studio（BSL-1.1）与 Pagekin（GPL-3.0）均**只借鉴设计与交互模式，不复制源代码**。

- 不引入其代码片段、组件实现、样式资源。
- 可借鉴：页面信息架构、状态机划分、上下文组装策略、运行可观测性的交互设计。
- 若未来改为对外分发，此约束不变。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| Electron 桌面优先 | 放弃多端访问；本地 SQLite 无法支撑多用户与审计；与 Postgres 权威模型冲突 |
| 以会话为中心（ekko 形态） | 小说创作是长周期文档工作，聊天中心会使用户每次动笔都要多轮对话，且产出难以版本化 |
| 首发即多 agent | 16 个适配器的复杂度（配置隔离、超时、限流回退）会拖慢 M2/M3 的核心闭环 |
| Vue 3 + Koa 复刻 ekko | 与 M0 既定的 React + FastAPI + Postgres 冲突；Node 与 Python agent 之间还需额外桥接层 |

## 正面影响

- 形态与部署简单，浏览器即用，后续可通过反代暴露到局域网或公网。
- 文档为唯一主体，版本、审批、审计有天然落点，符合 M2 的"正式版本不可静默覆盖"。
- Python 前后端同语言，减少一层进程桥接与序列化问题。
- Agent 契约先窄后宽，避免为未使用的集成付出设计成本。

## 风险与代价

- 纯 Web 无法直接操作本地文件，导入 `.txt/.epub` 需走上传与服务端解析，大文件与私有格式处理成本上升。
- 放弃桌面端意味着没有系统级能力（托盘、离线、本地模型直连），本地模型需用户自行暴露 HTTP 端点。
- 单 agent 首发可能让"可接不同 agent"的产品定位在早期无法被验证。
- 仅借鉴设计而不复用代码，界面工作量显著高于直接 fork。

## 兼容性与迁移影响

- 与现有 `skill/` 资产无冲突：Skill 保持 Markdown 文件形态，Studio 通过受控适配读写。
- 与 M0 既定的 Postgres 权威模型一致，不需要调整数据架构方向。
- 若后续增加客户端/桌面壳，领域服务层与数据层无需改动，仅新增一个前端容器。

## 复审条件

出现以下情况需重新审视本决策：

1. 用户明确要求离线或本地文件系统能力；
2. Hermes 的进程内集成方式发生根本变化（如改为纯 HTTP 服务）；
3. 第二个 agent 接入时，现有 `AgentAdapter` 契约无法覆盖其能力模型；
4. 产品确定对外分发，且许可或品牌要求影响架构选择。
